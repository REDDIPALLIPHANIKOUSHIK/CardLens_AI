# CardLens AI

**Credit-card recommendations you can inspect, compare, and question.**

CardLens AI is a fintech decision-support demo. A user enters a spending and eligibility profile; the backend filters and ranks a small card catalog, then explains the trade-offs behind its suggestions. The catalog is synthetic, so this project demonstrates the product and engineering approach—not current offers or financial advice.

## What to look at first

- **Recommendation engine:** `backend/app/main.py` — eligibility checks, six-factor suitability score, reward estimate, and explanations.
- **Account and persistence model:** `backend/app/auth.py`, `backend/app/models.py`, and `backend/migrations/` — sessions, user data, and schema history.
- **API and assistant tools:** `backend/app/main.py`, `backend/app/ai/`, and `backend/app/rag.py`.
- **Web experience:** `frontend/src/App.tsx` and `frontend/src/AuthGate.tsx`.
- **Architecture and deployment:** [architecture](docs/architecture.md), [local deployment](docs/deployment.md), and [Vercel deployment](deployment-vercel.md).

## The product in a few minutes

1. Create an account and complete the guided profile with income, credit score, spending, fee preference, and reward preference.
2. Review ranked recommendations, including the suitability score breakdown, estimated net annual value, fit reasons, and trade-offs.
3. Save cards, compare a selected pair or trio, and try a What-If scenario to see how a profile change affects the ranking.
4. Ask the CardLens Advisor about the result. It can explain the deterministic calculations and, when configured with verified indexed material, answer supported card-knowledge questions with source information.

## How recommendations work

Recommendations are calculated by the Python backend, not generated by a language model. Known minimum income and credit-score requirements are applied first. Eligible cards are then scored using six weighted factors: spending match, estimated reward value, reward preference, known eligibility, annual-fee fit, and benefits.

The API returns the score breakdown and the reasons for and against each match. The score describes fit with the supplied profile; it is **not** an approval probability. Missing profile values stay unknown rather than being guessed. What-If uses the same ranking path with temporary inputs, so it does not silently change the saved profile.

Reward estimates use the catalog's illustrative reward rates and the user's declared spending, less the listed annual fee. Real issuer caps, exclusions, redemption rules, and current terms are not modeled.

## Architecture

```text
React + TypeScript + Vite
          │ same-origin /api requests
          ▼
FastAPI + Pydantic ── deterministic eligibility and ranking
          │
          ├── SQLAlchemy + Alembic ── PostgreSQL / pgvector
          └── optional LLM, embeddings, speech providers
```

PostgreSQL stores accounts, profiles, saved-card relationships, and user activity. Alembic owns schema changes. The included catalog is still an in-memory set of clearly labeled synthetic offers; `scripts/seed_database.py` loads corresponding demo records for database-backed features.

The Advisor is an optional layer around the core calculations. It can route supported questions to deterministic tools; retrieval-backed card facts require indexed source material. With AI credentials unset, recommendations and core profile flows remain deterministic, and voice features can use browser speech where available.

## Technology

- **Frontend:** React, TypeScript, Vite, and Lucide icons.
- **API:** FastAPI and Pydantic.
- **Persistence:** SQLAlchemy, Alembic, PostgreSQL, and pgvector.
- **Optional AI:** replaceable LLM, embedding, speech-to-text, and text-to-speech adapters.
- **Delivery:** Docker Compose, GitHub Actions, and a Vercel multi-service configuration.

## Run locally

You’ll need Python 3.11+, Node.js 20+, and PostgreSQL with the `vector` extension for account and persistence features. From the repository root:

```powershell
Copy-Item .env.example .env
python -m venv .venv
.venv\Scripts\Activate.ps1
python -m pip install -r backend/requirements-dev.txt
```

Set `DATABASE_URL` in your local environment to your PostgreSQL database. Keep credentials out of source control. Apply the existing migrations and add the illustrative catalog records:

```powershell
python -m alembic -c backend/alembic.ini upgrade head
python scripts/seed_database.py
```

Start the API in one terminal:

```powershell
python -m uvicorn backend.app.main:app --reload
```

In a second terminal, start the web app:

```powershell
cd frontend
npm install
npm run dev
```

Open `http://localhost:5173`. The API runs at `http://localhost:8000`; interactive API documentation is at `http://localhost:8000/docs`. In local Vite development the frontend defaults to the local API. For Vercel's single-domain setup, leave `VITE_API_BASE_URL` unset so requests use same-origin `/api/...` routes.

For a containerized demo, use [docs/deployment.md](docs/deployment.md). For Vercel configuration and production environment variables, see [deployment-vercel.md](deployment-vercel.md).

## Useful API routes

| Route | What it does |
| --- | --- |
| `POST /api/auth/signup`, `POST /api/auth/login` | Create an account or start a session |
| `GET /api/profile`, `PUT /api/profile` | Read or save the signed-in user's profile |
| `POST /api/recommend` | Calculate ranked recommendations |
| `POST /api/simulate` | Recalculate with temporary What-If changes |
| `POST /api/compare` | Compare two or three eligible cards |
| `GET`, `POST`, `DELETE /api/favorites...` | List, save, and remove the signed-in user's saved cards |
| `POST /api/chat` | Ask the Advisor using available deterministic tools and configured providers |
| `GET /api/health`, `GET /api/ready` | Check API liveness and database readiness |

The complete interactive route list is available at `/docs` while the API is running.

## Configuration and migrations

`.env.example` lists local settings. The main production settings are `APP_ENV`, `DATABASE_URL`, and `FRONTEND_ORIGINS`; optional server-side integrations use `LLM_API_KEY`, `EMBEDDING_API_KEY`, and `VOICE_API_KEY` with their provider settings. Keep secrets on the backend—never place them in a `VITE_*` variable.

To apply the database schema from the repository root:

```bash
python -m alembic -c backend/alembic.ini upgrade head
```

This applies the existing Alembic chain through its current head. It does not replace the database or provide a second schema-management path. Production migrations are run explicitly; they are not coupled to every Vercel deployment. The repository also includes a manually triggered GitHub Actions migration workflow that reads the `DATABASE_URL` repository secret.

## Interview notes

### Why keep ranking deterministic?

Eligibility and numeric estimates need repeatable behavior that can be inspected and tested. The score breakdown lets a reviewer trace a recommendation to its inputs. An LLM may help explain a result, but it does not choose the winner or calculate the score.

### How would you make the catalog production-grade?

Replace the synthetic constants with issuer-verified, source-linked records; model caps, exclusions, fees, and redemption constraints; track when each term was verified; and monitor for changes. The current demo intentionally does not represent these details as real offers.

### What would you improve next?

Add consent and retention controls, broader browser-level accessibility and interaction tests, distributed rate limiting for multi-instance deployments, and an evaluation dataset before making recommendation-quality claims. Provider-backed LLM, RAG, and voice behavior also needs validation with real credentials and source material.

For a deeper discussion, see [interview preparation](docs/interview-preparation.md), [implementation status](docs/implementation-status.md), and [architecture](docs/architecture.md).

## Important limitations

- The current card catalog and its rates are synthetic illustrations, not real or up-to-date issuer offers.
- CardLens does not make an issuer decision or promise approval. Actual eligibility and terms come from the issuer.
- No labeled user-choice dataset is available, so the project makes no predictive-accuracy claim.
- Consent workflows, email account recovery, distributed rate limiting, and production monitoring are not complete.
- Optional model, retrieval, and speech integrations depend on external credentials and are not required for deterministic recommendations.

Please use sample profile data for demos. Do not enter bank credentials, payment-card numbers, CVVs, or other highly sensitive financial information.
